# Alpha status

kernl is a first draft. This page says what runs, what is a contract without an implementation, and which upstream gaps are open. It is updated in the same pull request as the code it describes.

## What works

| Area | Package | State |
| --- | --- | --- |
| Guard | `@kernlize/guard` | Three profiles (`createGuardConfig`), envelope classification, ingress flood control with quarantine, visibility gate, focus-aware rate limiter over `@kehto/rate-limit`'s `evaluateRateLimit`, the fixed zero-network CSP, an insertion lock on top of kehto's nested-context lock ([D-014](./decisions.md#d-014)), twelve mitigation descriptions for the UI. Pure, fully specified in `packages/guard/features/`. |
| Messaging | `@kernlize/messaging` | `MessagingProvider`, `MessagingBackend`, `MessagingRegistry` with saved-preference restore, the composite backend with `provider:innerId` namespacing, `describeProvider` rows, a complete in-memory backend (`createMemoryBackend`) used by the preview and the tests, and three providers (`private`, `legacy`, `ratchet`) built with `defineProvider` from backends the shell injects. The network backends for `private` and `legacy` are in `@kernlize/core` (`createPrivateMessagesBackend`, `createLegacyMessagesBackend`) and are wired in the live shell ([below](#messaging-providers-in-the-live-shell)). |
| Bridges | `@kernlize/bridges` | `Locator` parsing for the web schemes, `magnet:`, `nzb:`, `slsk:` and `mailto:`, the `Bridge` contract, the registry with its `authorize` hook and outcome events, a complete HTTP bridge with SSRF policy, the four backend-driven bridges up to their backend interface, `createHandoffBackends`, which serves all four by opening the locator in an app on the user's device, `createWebTorrentBackend`, which downloads magnet links inside the shell page over WebRTC, `createBridgeResourceResolver` for kehto's resource service, `describeBridge` rows, and adapters that drive Transmission, uTorrent, NZBGet, SABnzbd and slskd through each program's own HTTP API, with the address check they share ([D-050](./decisions.md#d-050)). Transmission 4.1.4, NZBGet 26.3, SABnzbd 5.1.3 and slskd 0.26.2 were run against the adapters; uTorrent was not, and slskd's search results and transfers were not observed. |
| Composition | `@kernlize/core` | `createKernl` over one applesauce `EventStore`, `RelayPool` and `AccountManager`, with kehto's real `createShellBridge` exercised end to end in `kernl.feature`: an applet is decoded, resolved, planned and mounted, binds its port through the guarded `handleWindowMessage`, completes `shell.ready`, is answered by the theme, identity and resource services, and is quarantined and revoked when it floods. Relay tiers, the applesauce adapters, the guard pipeline and the runtime's rate limiter, the firewall (`firewall.feature`, `firewall-adapters.feature`), grants over `bridge.runtime.aclState`, consent summaries, the default registries and the layouts each have their own feature file. The `torrent`, `nzb` and `soulseek` services, the download program settings and the secrets providers have theirs too; the services are exercised through kehto's runtime in `kernl-downloads.feature` with `downloads.offer` set, because the installed prelude does not bind them yet (see below). |
| Controller input | `@kernlize/modules` | A granted applet receives live controller snapshots only in the focused window. The port and the grant are exercised in `gamepad.feature` ([D-075](./decisions.md#d-075)). |
| Shell UI | `apps/web` | Landing site at `/` and the shell at `/app/`: sign-in (browser extension, remote signer, read-only, password-protected local account, or a throwaway identity that is never stored, [D-044](./decisions.md#d-044)), open by address with the required and optional domains as choices, windows, a grants panel per window, a shell-wide guard panel with the event log, a firewall panel and the firewall's questions ([D-056](./decisions.md#d-056)), the provider picker, and the preview behind `?preview=1`, the real kernel and kernl's own modules over relays that live in the page ([D-070](./decisions.md#d-070)), hosted at [kernl.run/app/?preview=1](https://kernl.run/app/?preview=1). |

"Works" means the behaviour has a scenario in `packages/*/features/`, the scenario passes, and the page describing it exists. It does not mean the API is stable. Every package is `0.1.0`; on 0.x a breaking change is a minor bump.

## Messaging providers in the live shell

`createKernl` loads the messaging module with all four providers and wires real backends, among them two from `@kernlize/core`: `createPrivateMessagesBackend` for `private` (NIP-17 gift-wrapped messages) and `createLegacyMessagesBackend` for `legacy` (NIP-04 direct messages). Both sign and encrypt with the active account's signer and nothing else ([D-015](./decisions.md#d-015)). Availability follows the active account, and an unavailable provider reports a reason from `MESSAGING_UNAVAILABLE_REASONS`:

| Provider | Available when | Reason otherwise |
| --- | --- | --- |
| `private` | The active account's signer exposes `nip44` (browser extension, remote signer, password-protected local account) | `sign-in-required` with no active account; `signer-cannot-encrypt` when the signer has no `nip44` (a read-only account) |
| `legacy` | The active account's signer exposes `nip04` | `sign-in-required` with no active account; `signer-cannot-encrypt` when the signer has no `nip04` |
| `ratchet` (experimental) | The active account's signer exposes `nip44`, which seals the session state kept on this device | `sign-in-required` with no active account; `signer-cannot-encrypt` without `nip44` |
| `group` (experimental) | The active account's signer exposes `nip44`, which opens invitations and seals the group state kept on this device | `sign-in-required` with no active account; `signer-cannot-encrypt` without `nip44` |

`private` sends to the recipient's kind 10050 inbox relays, falling back to the sender's `outbox` and `super` tiers when the recipient publishes none, and wraps a copy to the sender so the conversation reads the same on every device. `legacy` is metadata-exposing: sender, recipient and timing are public on the event, and the picker says so. Messages are shown by an applet over the `dm` domain grant. kernl ships one, pinned by hash and opened without a lookup; it starts with the grants it needs and the user can withdraw each ([D-027](./decisions.md#d-027)). `private` and `legacy` are switched on for someone who has never chosen, the user orders the providers in Settings, and a reply to someone who last wrote through another provider is asked about first. The preview runs the same applet, with `private` and `legacy` over in-memory backends where two scripted people have already written.

Known gaps in messages: the applet cannot say which provider carried a message, so after the question is answered the choice is visible only in Settings; a request another applet hands over to open a conversation opens Messages but not yet that conversation (the applet's toolkit version has no delivery hook); and the toolkit gives up on a send after thirty seconds, so a reply question left open longer shows the message as still sending until the shell reports it.

## What does not work yet

- **The download domains in the live shell.** The settings work: a person can connect Transmission, uTorrent, NZBGet, SABnzbd or slskd under Settings, Downloads ([Connect a program](./how-tos/connect-a-download-program.md)). No applet can use them yet. `torrent`, `nzb` and `soulseek` are offered only when the installed `@kehto/shell` prelude renders a binding table ([kehto/web#413](https://github.com/kehto/web/pull/413)), and 0.35 does not, so the services are not registered and the store marks an applet that requires one as it marks any applet this shell cannot run. When they are offered they are remote controls: an applet can start, watch and steer a transfer, and cannot read, save or open the files, which are on the program's disk. From a browser page Transmission and uTorrent need a reverse proxy in front, because they do not accept requests from another origin. On kernl.run the programs' passwords and keys are kept in the browser's storage as typed; a protected keeper needs a host that passes its own [secrets provider](./concepts/secrets.md) ([D-052](./decisions.md#d-052)). See [Connected programs](./concepts/download-programs.md).
- **In-shell transfers for NZB, Soulseek and mail.** Magnet links download inside the shell page by default ([D-017](./decisions.md#d-017)): a WebTorrent client loaded on the first download reaches browser peers over WebRTC, and the Downloads panel shows progress and lets the user pause, resume, remove and save. It reaches only peers that speak WebRTC, so a link whose swarm has none stays "Looking for peers"; the user can switch to "Open in an app on your device" in Settings. Downloads live in memory and end when the tab closes. NZB, Soulseek and mail still work only by hand-off, after the user confirms leaving kernl, because their protocols need raw TCP sockets a page cannot open. A `job` result from a hand-off is an id, not a transfer kernl can track, and it is reported even when the user declines to leave. See [Bridges](./concepts/bridges.md#downloads-inside-kernl).
- **Ratchet sessions, beyond one to one on a shared relay.** `ratchet` works in the live shell ([D-016](./decisions.md#d-016)) but is experimental: sessions are one to one, both sides must share an `outbox` or `super` relay, the conversation list is in memory and empties on reload (sessions and keys survive, sealed to the account), the first use waits up to the library's 12 s for the account's device list, and an extension or remote signer is asked to decrypt each stored value once per page load and to encrypt each write. In the preview it runs over relays that live in the page, where nobody else speaks it. See [Messaging](./concepts/messaging.md).
- **Group sessions, beyond the basics.** `group` works in the live shell ([D-018](./decisions.md#d-018)) but is experimental and runs an alpha library: messages are kept in memory, so a reload empties each group's history (membership and secrets survive, sealed to the account); an account is one member of a group, so only one of a person's devices joins it; people can be added only when they have published a key package, which kernl does when the provider is first used; there is no way yet to name a group, add or remove members after it starts, or leave it; and an extension or remote signer is asked to decrypt each sealed store once per page load and to encrypt each write. Relay-based groups (NIP-29) are not offered, because they are not end-to-end encrypted. In the preview it runs over relays that live in the page, where nobody else has published a key package, so there is nobody to invite. See [Messaging](./concepts/messaging.md#protocol-inventory).
- **Web fetch from the browser shell, beyond the simple case.** The HTTP bridge runs in the page, so it is subject to CORS, and an opaque redirect it cannot inspect is refused with `denied:redirect-unverifiable`. Web fetch works from the shell for `https` origins that permit cross-origin reads and answer without a redirect. Hostnames are checked as literals only; no resolver is wired. See [Bridges](./concepts/bridges.md#the-http-bridge).
- **Per-host bridge consent.** `createKernl` builds the bridge registry with `createDefaultBridges()` and no `authorize` hook, so a `resource` request from a granted applet is checked by the HTTP bridge's SSRF policy and nothing else. A host that wants a prompt per host or scheme passes its own registry in `KernlOptions.bridges`.
- **The firewall, beyond the first rules.** kehto's firewall decides every request ([D-056](./decisions.md#d-056)), with three known gaps. Only a download's first origin reaches the firewall, because the bridge registry follows redirects under its own address policy. The relay plan for messages and social actions names every relay in the shell's tiers, not the recipient's inboxes. An upload's plan names the first file server, not its mirrors. The firewall panel sets rules for everything, by kind, and per open applet for links only; other per-applet rules need `kernl.firewall.setRule`. See [Guard](./concepts/guard.md#the-firewall).
- **Per-applet guard profiles.** `GuardFacade.setProfile` rebuilds the pipeline for the whole shell and is not persisted. The per-applet, remembered override [D-003](./decisions.md#d-003) describes is not in this draft.
- **Mobile layouts beyond the basics.** The layouts are desktop tilings over `@kehto/wm` ([Layouts](./concepts/layouts.md)). At 720 px wide and below the shell switches to a compact layout: every window fills the desktop, and the bar keeps **Open** and moves the guard, messages, layout, minimised windows, settings and sign-out into a **Menu** sheet; panels open as full-width sheets. There are no gestures. Every open window is reported to the guard as visible there, although only the front one can be seen: kernl's window manager does not yet treat a window wholly covered by another as hidden ([Layouts](./concepts/layouts.md#what-the-guard-is-told)).
- **Multi-account switching.** `AccountManager` holds several accounts and the sign-in panel lists them, but switching means signing out and in.
- **Grant persistence across devices.** Grants, relay tiers and messaging preferences persist in the host's storage only. There is no sync. Every key is listed in [Persistence](./concepts/persistence.md).
- **Published packages.** Nothing is released yet, neither `@kernlize/*` on npm nor `@kernl/*` on JSR; they are used from a clone of the source repository, which is private during the alpha. See [Packages](./packages/index.md#install).
- **Source links in the API reference.** `typedoc.json` sets `packageOptions.disableSources: true`, so the generated reference has no "Defined in" source links. They would point at the source repository, which is private during the alpha.

The [Roadmap](./roadmap.md) orders this list.

## Upstream gaps

kernl composes kehto rather than forking it ([D-001](./decisions.md#d-001)). The four seams kernl filed against `kehto/web` ([#397](https://github.com/kehto/web/issues/397), [#398](https://github.com/kehto/web/issues/398), [#399](https://github.com/kehto/web/issues/399), [#400](https://github.com/kehto/web/issues/400)) are closed in `@kehto/shell` 0.32.0, `@kehto/runtime` 0.28.0 and `@kehto/firewall` 0.7.0, and kernl uses them ([D-020](./decisions.md#d-020)):

1. **Firewall hooks through `ShellAdapter` (#397).** kernl passes `getFocusContext` (only `focused`). `onFirewallEvent` and `legacyFirewall`, which this seam also added, are no longer passed: `permissions` replaced them ([D-056](./decisions.md#d-056)).
2. **ACL default policy (#398).** The adapter sets `aclDefaultPolicy: 'restrictive'`. `KernlGrants.ensure` grants the baseline and the user's domains and revokes only what an applet's stored entry holds beyond them.
3. **A hook that can hold or drop port traffic (#399).** `filterNappletMessage` runs kernl's guard pipeline for every port envelope. What the guard will not let through is dropped, with no reply to the applet. A hidden window's requests are held and released with `releaseDeferred` when it is visible. See [Guard](./concepts/guard.md#where-enforcement-happens).
4. **Unfocused multiplier and burst guard setters (#400).** No longer used. Each class budget kernl hands the runtime carries the profile's `unfocusedMultiplier`, the configuration is read on every charge, and kernl configures no startup burst ([D-056](./decisions.md#d-056)).

kernl's own layers stay in front of kehto where kehto cannot see what they see: envelope size for downloads and queries, window visibility, a separate deletion budget, and flood quarantine. The focus-aware rate limiter overlaps the runtime's and stays so that kernl's own decisions remain a complete source of guard events ([D-020](./decisions.md#d-020)).

[kehto/web#336](https://github.com/kehto/web/pull/336) made kehto's firewall a shared approval authority, configured through `permissions`, and moved rate limiting into the optional `@kehto/rate-limit`. kernl has moved ([D-056](./decisions.md#d-056)): `createFirewallPermissions` configures `permissions` with the user's rules, `createRuntimeRateLimiter` is `permissions.rateLimiter`, and `@kernlize/guard` runs `evaluateRateLimit` from the package's main entry. The `/legacy` subpath, `legacyFirewall`, `onFirewallEvent`, `guard/runtime-rules.ts` and the `kernl:firewall:v1` key are gone, and the `FW-*-LEGACY-*` warnings with them. What the firewall does not yet see is listed under [What does not work yet](#what-does-not-work-yet).

The intent gap is closed. `@kehto/acl` 0.20.6 maps `intent.deliver` to `intent:read`, so kernl delivers through the runtime's `sendToEligibleNapplet` ([D-037](./decisions.md#d-037)).

One gap is open for the download domains ([D-050](./decisions.md#d-050)). kehto's runtime dispatches a domain it does not build in to a service that lists its message types, but the prelude it injects into an applet builds such a domain as an empty object, and the port the applet talks through is private to that prelude. [kehto/web#413](https://github.com/kehto/web/pull/413) lets a host pass the prelude a binding table per domain; it is not in a release as of `@kehto/shell` 0.35. kernl declares the table's shape locally (`DomainBinding`), asks the installed prelude whether it renders one (`supportsDomainBindings`), and offers the three domains only when it does. No second channel into the applet is built in the meantime.

A fifth observation, not a gap kernl needs closed: the transport internals `createNip5dTransport` and `createShellReadyState` are not exported, so kernl uses `createShellBridge` unchanged.

One mitigation goes beyond kehto: `@kehto/shell` 0.30.0 ships `experimental.nestedContextLock`, which stops an applet creating a child frame whose fresh realm still has WebRTC, and `planMount` always enables it. kehto's lock guards creation only, and four creation routes get past it (a customized built-in constructed with `new`, XSLT, and a namespace-prefixed XHTML element brought in with `importNode` or `adoptNode`), so `@kernlize/guard` adds an insertion lock on top until kehto guards insertion. The routes are to be reported to kehto ([D-014](./decisions.md#d-014)).

## Corrections

- **Rate enforcement (corrected 2026-11-03).** Earlier drafts of these docs, the README and D-012 said kehto's runtime firewall refused envelopes over the profile's rates. It did not: `applyRuntimeFirewallRules` also set each applet's runtime policy to `allow`, and kehto's `evaluate()` returns `pass` for an `allow` policy before it looks at any rate, matcher or burst. No rate was refused before dispatch; only kernl's reports and quarantine applied. The policy call is removed, the rates and kehto's startup burst guard now refuse before dispatch, and D-012 is rewritten to match.
- **Size caps (corrected 2026-11-03).** The guard's size matchers were described as able to report `matcher:size:<class>` in the shell. They cannot fire there: the ingress guard rejects the same envelopes first. Oversized downloads and queries were reported but still handled; they are now refused before dispatch.
- **Focus tightening, bursts and hidden windows (changed 2026-11-04).** These were reported to the user but still handled. They were then refused before dispatch the same way size caps were (`refuseCurrentDispatch`): a request over the smaller unfocused budget, a request in a burst above the per-second rate, and any non-control request from a hidden window got a `firewall:` error. Control envelopes were never refused. See [D-012](./decisions.md#d-012).
- **Dropped and held, not refused (changed with kehto 0.32.0).** kernl now decides each port envelope through kehto's `filterNappletMessage`. Oversized requests, bursts and requests over the unfocused budget are dropped and get no reply; a hidden window's requests are held and answered once it is visible. The runtime's startup burst is the profile's (8 operations in a window's first second in `strict`) rather than kehto's default of 20 in 3 s. See [D-020](./decisions.md#d-020).
- **The firewall and rate limiting (changed 2026-11-20).** kehto's firewall became an approval authority and kernl configures it: every applet start and every request is decided under rules that allow what was granted and ask about every link. The runtime's rates come from `createRuntimeRateLimiter`; a refusal reads `rate limit exceeded`, not an error starting `firewall:`, and the runtime no longer has a startup burst. The guard event reasons `flood:startup`, `runtime:<ruleId>`, `matcher:<id>`, `policy:deny` and `prompt:<ruleId>` no longer occur, and `flood:prompts` is new. A window kehto was handed without `kernl.plan` gets no answer at all, where it used to be served as the shell's own. See [D-056](./decisions.md#d-056).
